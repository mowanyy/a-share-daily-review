# 版本管理约定（Git 工作流）

> 目的：**每轮对话结束自动提交 + 功能完成合并 + 标注版本 + 上传**，保证工程可回溯、可复现。
> 版本号由 AI 根据**工作量和改动大小**标注（用户已授权）。
> 当前：远程 `origin`（`mowanyy/a-share-daily-review`，public）已配置，push 走 `git push origin main --tags`（直连需加速器，或用 `-c http.proxy= -c https.proxy=` 绕过全局代理）。

---

## 0. 分支策略总览（v0.37.1 引入）

单开发者 + AI 协作的**轻量 GitHub Flow 变体**：只有 `main` 长期分支；新功能/较大改动开临时 feature 分支，完成时 **squash 合并**回 main 并 bump 版本；小修直接提交 main。

| 分支 | 角色 | 生命周期 |
|---|---|---|
| `main` | 唯一长期分支，**永远可发布**（每个提交都通过全量测试） | 永久 |
| `feature/<功能名>` | 新功能/重构/较大改动的开发分支（如 `feature/agent-eval`） | 开发完 squash 合并 → 删除 |
| `data-branch` | 孤儿数据分支，`push-review.yml` 每日自动 force push 数据/产物快照 | **不动**（全自动维护，与 main 隔离） |

**为什么不用 Git Flow**：单开发者无并行团队、无发布窗口，`develop`/`release`/`hotfix` 分支是负担；`main` 即最新即发布。三个 GitHub Actions workflow 只监听 `schedule` + `workflow_dispatch`，feature 分支 push 上去零 CI 副作用。

**串行为主**：默认一个时间只存在一个 feature 分支，避免并行分支堆叠。

## 1. 版本号规则（语义化版本 MAJOR.MINOR.PATCH）

项目处于 `0.x` 开发期。版本推进规则：

| 改动类型 | 例子 | 版本推进 |
|---|---|---|
| **PATCH（小改）** | 修 bug、补文档、环境同步、测试调整、格式化 | `0.2.0 → 0.2.1` |
| **MINOR（新功能）** | 新增涨停池/炸板池爬虫、指标计算、LLM 报告、问答模式 | `0.2.x → 0.3.0` |
| **MAJOR（架构级）** | 架构重构、或正式发布 | `0.x → 1.0.0` |

- **bump 时机（v0.37.1 起）**：**功能合并回 main 才 bump**。feature 分支开发期间不 bump、不打 tag；合并时 MINOR 推进一次并打 tag。小修直推 main 时 PATCH 推进。每个 tag 对应一个完整可用的功能点，版本增速放缓。
- 提交时同步更新 `pyproject.toml` 的 `version` 字段，二者保持一致

## 2. 分支工作流

### 2.1 新功能 / 较大改动（走分支）

```bash
# ① 从 main 最新处开分支
git checkout main && git pull
git checkout -b feature/<功能名>        # 如 feature/agent-eval

# ② 分支内按轮次迭代提交（Commit 格式见第 4 节）
#    不 bump 版本号、不打 tag；功能未完成就停在分支上
git add -A && git commit -m "feat(<scope>): <简述>"

# ③ 完成时：测试通过 + 状态审查 → 合并回 main
python -m pytest
git status --short
git checkout main
git merge --squash feature/<功能名>     # squash：分支内碎提交折叠成 1 条
git commit -m "feat(<scope>): <功能简述>"

# ④ bump 版本 + 打 tag + 上传 + 删分支
#    改 pyproject.toml version（MINOR 推进）后：
git add pyproject.toml && git commit -m "chore(release): v0.38.0"
git tag v0.38.0
git push origin main --tags
git branch -d feature/<功能名>
```

- 合并前若 main 有新提交：先 `git rebase main`（或 `git merge main`）解决冲突，再 squash。

### 2.2 小修（直接提交 main）

修 bug / 补文档 / 环境同步 / 测试调整 / 格式化：**不开分支**，直接提交 main，bump PATCH 并打 tag：

```bash
git add -A && git commit -m "fix(<scope>): <简述>"
python -m pytest
# 改 pyproject.toml version（PATCH 推进）后：
git add pyproject.toml && git commit -m "chore(release): v0.37.1"
git tag v0.37.1
git push origin main --tags
```

### 2.3 回滚纪律

- 已 push 的 main 历史一律 `git revert`（生成反向提交），**禁止 `git reset` 改写公共历史**。
- tag 一经推送不可移动或删除重打（破坏可复现性）。

## 3. 提交流程（每轮对话结束时执行）

```bash
# 1. 提交前检查
git status --short          # 确认改动范围、确认无 data/*.csv 入库
python -m pytest            # 测试通过再提交

# 2. 提交到当前分支（feature 分支或 main）
git add -A
git commit -m "<type>(<scope>): <简述>"

# 3. 标注版本 —— 仅两种情况打 tag：
#    a. 功能合并回 main（MINOR 推进，见 2.1）
#    b. 小修直推 main（PATCH 推进，见 2.2）
git tag v0.x.y

# 4. 上传（远程配置后）
git push origin main --tags
```

## 4. Commit 消息格式

```
<type>(<scope>): <简述>

示例：
  feat(data): 实现东财涨停池接口
  docs(env): 同步开发环境文档
  fix(cli): 修复控制台中文编码
  chore: 初始化 git 仓库
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 |
| `docs` | 文档 |
| `refactor` | 重构（不改行为） |
| `test` | 测试 |
| `chore` | 构建/杂项/初始化 |

| scope（常用） | 含义 |
|---|---|
| `data` | 数据采集层 |
| `prompts` | Prompt 工程 |
| `docs` | 文档 |
| `cli` | 命令行 |
| `env` | 环境/依赖 |
| `(空)` | 全局性改动 |

## 5. 入库 / 不入库

- **入库**：`docs/` `prompts/` `src/` `tests/` `knowledge/` `skills/` `requirements*.txt` `pyproject.toml` `.gitignore` `.gitattributes` `CLAUDE.md` `README.md`
- **不入库**（`.gitignore`）：`data/*/` `output/*/` `*.csv` `models/` `.kb_cache/` 缓存与虚拟环境目录
